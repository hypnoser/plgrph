# PLGRPH — сайт (plgrph.com)

Статичний сайт на Eleventy (11ty). Хостинг — GitHub Pages, DNS — Cloudflare
(без Cloudflare Worker — навмисно, історія проблем описана в README проєкту
[krzhv](https://github.com/hypnoser/krzhv)).

## Технічний стек

- **Генератор:** Eleventy (11ty) v3
- **Шаблони:** Nunjucks (`.njk`)
- **Хостинг:** GitHub Pages
- **DNS:** Cloudflare (bare domain plgrph.com, без Worker у шляху запиту)
- **Шрифти:** Manrope (заголовки), Inter (текст) — self-hosted WOFF2

## Структура проєкту

```
src/
  _layouts/       — базові шаблони сторінок (base.njk)
  _includes/      — партіали (header, footer, maintenance overlay)
  assets/
    css/          — стилі, що не інлайняться в <head>
    fonts/        — self-hosted WOFF2 (Manrope, Inter) — довантажити вручну, див. нижче
    images/       — зображення, лого
  blog/           — статті блогу (markdown), колекція blogPosts
  index.njk       — головна сторінка
  robots.njk      — генерує /robots.txt
  sitemap.njk     — генерує /sitemap.xml з усіх колекцій
  llms.njk        — генерує /llms.txt
eleventy.config.js — конфіг: колекції, фільтри, passthrough-копіювання
```

## Важливо: /ps/ (Polygraph Suite)

Калькулятор `/ps/` — **окремий діючий продукт**, що вже живе в корені цього
репозиторію (поза `src/`). Його код і логіку **не чіпаємо**.

⚠️ **Критично для деплою.** Поточний сайт деплоїться через
Settings → Pages → "Deploy from a branch" — публікується весь корінь гілки
напряму, тому `/ps/` зараз живий просто завдяки фізичному розташуванню.
Після переходу на GitHub Actions (обов'язково для Eleventy-білду)
публікується **лише вміст `_site/`** — вихід Eleventy з `src/`. Щоб `/ps/`
не зник із живого сайту, `eleventy.config.js` явно копіює його незмінним:

```js
eleventyConfig.addPassthroughCopy({ ps: "ps" });
```

Це перевірено локальною збіркою — `/ps/`, `/ps/en/`, `/ps/es/` потрапляють
у `_site/ps/` побайтово без змін. **Не видаляти цей рядок з конфігу** і не
переносити `/ps/` всередину `src/` без окремого узгодження — калькулятор
має продовжувати оновлюватися своїм окремим робочим процесом, незалежним
від цього сайту.

## Maintenance overlay ("сайт на реконструкції")

Увімкнення на будь-якій сторінці — `maintenanceOverlay: true` у frontmatter.
Це HTML/CSS overlay, не JS-підміна — реальний контент сторінки лишається
в DOM і доступний пошуковим ботам (Google-safe підхід). Дисміс — прихована
48×48px click-зона у правому верхньому куті, зберігається per-browser через
localStorage (ключ `plgrph_maintenance_dismissed`).

Коли редизайн буде готовий до публікації — прибрати `maintenanceOverlay: true`
з frontmatter кожної сторінки (не видаляти сам include-файл — знадобиться
для майбутніх технічних робіт).

## Шрифти

- **Inter Variable** — вже включено в репозиторій (`src/assets/fonts/inter-var.woff2`), готовий до використання.
- **Manrope Variable** — ще НЕ включено. Офіційний проєкт шрифту перейшов з GitHub на власний сайт,
  тому автоматичне завантаження було недоступне в середовищі, де готувався цей каркас. Довантажте
  вручну одним із способів:
  - Google Fonts: https://fonts.google.com/specimen/Manrope → "Download family" → взяти variable-файл,
    або скористатися google-webfonts-helper для отримання прямого .woff2
  - Офіційний сайт шрифту (пошук "Manrope font Mikhail Sharanda")

  Покладіть отриманий файл як `src/assets/fonts/manrope-var.woff2` — шлях і `@font-face` в
  `src/_layouts/base.njk` вже налаштовані під цю назву, додаткових змін коду не потрібно.

## Контент-воркфлоу (статті блогу)

Кожна стаття — окремий файл у `src/blog/`. Дивіться приклад
`src/blog/PRYKLAD-shablon.md.example` — скопіюйте, перейменуйте на `.md`
з осмисленою назвою файлу (наприклад `mezhi-tochnosti-poligrafa.md` —
сама назва файлу не впливає на URL, той визначається з `title`).

### Поля frontmatter

```yaml
---
layout: post.njk
title: Назва статті
description: Короткий опис (1-2 речення) — для списку блогу та SEO
date: 2026-03-15
ogImage: /assets/images/blog/nazva-statti-cover.jpg
keywords: поліграф, точність, методологія
---

Текст статті у форматі Markdown.
```

- **`layout: post.njk`** — обов'язково, без змін. Визначає, що файл — стаття
  блогу (breadcrumbs, дата, автор, "Читайте також").
- **`title`** — заголовок статті. Використовується у `<h1>`, у списку `/blog/`,
  у блог-прев'ю на головній, у `<title>` вкладки, в Open Graph/Twitter Card
  (заголовок при поширенні в соцмережах чи месенджерах), в Article Schema
  (structured data для Google) і в BreadcrumbList (третій рівень хлібних
  крихт). Обов'язкове поле.
- **`description`** — короткий опис 1-2 речення. Використовується у списку
  `/blog/`, в `<meta name="description">` (текст під заголовком у видачі
  Google), в Open Graph/Twitter Card, в Article Schema. Обов'язкове поле.
- **`date`** — дата публікації у форматі `РРРР-ММ-ДД`. Визначає сортування
  (найновіші зверху скрізь) і `datePublished` в Article Schema. Обов'язкове
  поле.
- **`ogImage`** (необов'язкове) — шлях до зображення-обкладинки цієї
  конкретної статті, наприклад `/assets/images/blog/nazva-cover.jpg`.
  Використовується, коли статтю поширюють у Telegram/Facebook/Viber тощо —
  саме це зображення покаже прев'ю посилання. Якщо поле не вказати,
  використовується загальне зображення сайту (`og-image.jpg`) — стаття
  все одно матиме прев'ю, просто без індивідуальної картинки. Рекомендований
  розмір зображення — 1200×630px (як og-image.jpg), кладіть файл у
  `src/assets/images/blog/`.
- **`keywords`** (необов'язкове) — список ключових слів/тем через кому,
  наприклад `поліграф, точність, методологія`. **Важливо чесно розуміти
  призначення цього поля:** Google офіційно не використовує meta-keywords
  для ранжування вже понад 10 років — це поле НЕ впливає на SEO напряму.
  Це суто робочий орієнтир для вас самих: легше згадати, про що стаття,
  при плануванні наступних текстів чи майбутньому групуванні за темами.
  Ніде на сторінці не виводиться.

### Що впливає на реальний SEO/AI-пошук

Найбільший вплив на те, як стаття виглядає в Google і як її "розуміють"
AI-пошукові системи (ChatGPT, Perplexity, Google AI Overviews тощо), дають:
`title` і `description` (написані природною мовою, що відповідає реальним
пошуковим запитам — той самий підхід, що вже застосований на `/faq/`),
структура самого тексту (заголовки `##`, короткий самодостатній перший
абзац, що одразу відповідає на тему заголовка), і внутрішні посилання на
інші сторінки сайту в тексті статті.

### Що відбувається автоматично

Стаття автоматично з'явиться у списку `/blog/` та у блог-прев'ю на головній
(до 6 останніх — якщо статей стане більше 6, на головній лишаться
показуватись 6 найновіших, решта доступна повним списком на `/blog/`).
Article Schema, Open Graph, Twitter Card, BreadcrumbList (JSON-LD)
генеруються автоматично з `title`/`description`/`date`/`ogImage` —
редагувати HTML/JSON вручну не потрібно.

### Генерація статті через AI

Готовий промпт-шаблон для передачі іншій AI-моделі (ChatGPT, Claude,
Gemini) — файл `CONTENT-PROMPT-BLOG.md` у корені репозиторію. Містить
точну структуру виводу, узгоджену з полями вище, і покрокову інструкцію,
що робити з результатом.

## Контент-воркфлоу (сертифікати/дипломи, розділ "Кваліфікація" на /pro-specialista/)

Кожен сертифікат — окремий файл у `src/certificates/`. Дивіться готовий
приклад `src/certificates/PRYKLAD-shablon.md.example` — скопіюйте його,
перейменуйте файл на `.md` (важливо: приклад навмисно має розширення
`.md.example`, щоб не потрапляти в реальну збірку сайту; ваш новий файл
має закінчуватись на `.md`), наприклад `sertyfikat-poligraf-2013.md`,
і заповніть своїми даними:

```yaml
---
title: Назва сертифіката/диплома
order: 1                                    # порядок на сторінці, менше число = вище
image: /assets/images/certificates/ФАЙЛ.jpg
year: "2013"
issuer: Назва установи, що видала документ
---

Короткий опис документа (один-два абзаци).
```

Саме зображення (jpg) кладіть у `src/assets/images/certificates/` — шлях
у полі `image` має точно збігатися з назвою файлу.

**Розмір зображення:** оригінальну орієнтацію (портретну чи альбомну) можна
не міняти — на сторінці прев'ю показується квадратним кропом автоматично.
Рекомендований розмір: довша сторона ~1200px, JPEG якість 80-85% (баланс
чіткості й ваги файлу для швидкого завантаження). Не обов'язково точно —
Eleventy лише виводить файл як є, підготовка розміру на вашому боці.

Сторінка сама підхопить новий файл при наступному білді — редагувати
`pro-specialista.njk` не потрібно.

## Відомі технічні уроки (успадковано з krzhv, актуальні й тут)

- Перевіряти реальний збережений стан файлу після редагування через GitHub
  веб-редактор — збереження іноді мовчки не спрацьовує.
- Вставка багаторядкового YAML-frontmatter через веб-редактор GitHub може
  внести символи табуляції — ламає парсер Eleventy. Використовувати
  flow-style (однорядковий, JSON-подібний) YAML для складних блоків.
- Шляхи до зображень у Markdown — завжди абсолютні (`/assets/images/...`),
  не відносні.
- Якщо GitHub Actions білд падає з помилками Jekyll/Liquid — перевірити
  Settings → Pages → Source (має бути "GitHub Actions", могло тихо
  відкотитися на "Deploy from a branch").
- Якщо виникають дивні проблеми з кешуванням/застарілим контентом —
  перше, що перевірити, це наявність залишкового Cloudflare Worker,
  прив'язаного до домену.
